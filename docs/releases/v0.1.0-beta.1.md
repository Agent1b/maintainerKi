# maintainerKi v0.1.0-beta.1 — First Public Beta

maintainerKi is an open-source, self-hosted GitHub triage assistant for issues and pull requests.

This first public beta is for maintainers who want to run their own triage stack: bring your own GitHub App, choose your own supported scoring backend, and keep your own infrastructure and secrets under your control.

## Highlights

- GitHub webhook intake for **issues** and **pull requests**
- Signature verification, replay/idempotency handling, and repository filtering
- Async scoring pipeline with **FastAPI + Celery + PostgreSQL + Redis**
- Supported scoring providers: **`ollama`**, **`mlx`**, and **`mock`** for smoke testing
- Duplicate detection with dashboard visibility and optional GitHub duplicate comments
- Maintainer dashboard with inbox, detail view, filters, stats, and feedback loop
- Optional GitHub label write-back
- Setup wizard for validating GitHub App credentials and selecting monitored repositories
- Self-hosted deployment path with Docker Compose, hosted HTTPS docs, retention tooling, smoke tests, and release-audit automation

## Current scope

This beta is intentionally narrow:

- **self-hosted only**
- **single-admin workflow**
- **bring your own GitHub App**
- **bring your own model/scoring backend**
- best treated as a **private maintainer console**, not a public SaaS

## Important limitations

maintainerKi is **not** yet:

- multi-user or role-based
- GitHub Marketplace-ready
- a public multi-tenant hosted service
- a fully autonomous moderation system

Maintainers stay in control of final triage and labeling decisions.

## Who this is for

- Solo maintainers
- Small trusted teams
- Self-hosters comfortable with Docker Compose, PostgreSQL, and Redis
- People who want to dogfood AI-assisted issue and PR triage on real repositories

## Not for

- Public SaaS deployments
- Multi-user org tooling with roles or permissions
- GitHub Marketplace distribution
- Teams expecting fully hands-off moderation

For packaged releases, publish from tracked Git files or the generated source snapshot — **not** from a raw workspace archive.

## Before you publish this beta

- enable **GitHub private vulnerability reporting** or add a real monitored security contact path in `SECURITY.md`
- commit the release-facing changes before tagging so the release matches the audited tree
- run `make release-audit` from the exact commit you tag
